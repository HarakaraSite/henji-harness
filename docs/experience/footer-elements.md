# フッター表示要素一覧

確認日: 2026-09-29

Increment 158の配置済み実装（source `aacf90cc`）を対象とした、通常HTTP接続TUIの現行表示一覧。
フッター整理前の表示であり、会話で検討した変更はまだ実装されていない。
画面幅によって要素が省略・短縮され、画面の高さが不足するとフッターの行数も減る。

[gpt-6-astraの整理案と利用者の追加判断](astra-proposal.md)も参照する。

## 1行目 — 操作案内・通知・状態・実行結果

現行では、この行に複数の種類の情報が混在している。

### 状態と受付通知

| 要素・表示例                              | 説明                                                                                                                                      |
| ----------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| `ready`                                   | 新規タスクを開始できる待機状態。working中も編集・追加指示は可能。現行では同じSessionの実行終了後に直近の結果が残り、自動でreadyへ戻らない |
| `idle`                                    | 通知と待機状態を組み合わせる際の表記。`ready`を短縮する処理でこの表記になる                                                               |
| `submitting`                              | 新しいタスクを送信中                                                                                                                      |
| `steering`                                | 実行中のタスクへの追加指示を送信中                                                                                                        |
| `queueing follow-up`                      | 現在の実行後に行うタスクを予約中                                                                                                          |
| `awaiting receipt`                        | Coreの受付結果を待っている                                                                                                                |
| `processing`                              | Core側で受付処理中。タスク送信やキャンセル要求の補足として表示される                                                                      |
| `requesting`                              | キャンセル要求を送信して受付結果を待っている                                                                                              |
| `accepted`                                | Coreが入力を受け付けた通知。実行中かどうかを示す状態ではない。現行では終了時に消されず、先頭に残る問題がある                              |
| `accepted, syncing snapshot`              | 入力の受付は確認できたが、Coreの状態更新を待っている                                                                                      |
| `accepted · waiting for core snapshot`    | 受付通知に、Coreの状態更新待ちを添えた表示                                                                                                |
| `preparing`／`task admission in progress` | タスクを受け付けて実行するための準備中                                                                                                    |
| `DISCONNECTED`                            | Coreとの接続が切れている                                                                                                                  |
| `last phase …`                            | 接続が切れる前に最後に確認したCoreの状態                                                                                                  |
| `READ-ONLY`                               | 閲覧中のSessionへタスクを送れない状態                                                                                                     |
| `shutting down Core`                      | Coreを終了中                                                                                                                              |

表示上の`idle`はreadyの別名だが、取消要求の応答`cancel idle`は対象が実行中ではないという結果であり、別の意味。
READ-ONLYはこのSessionへの新規タスク送信可否を表す。`/view`はactive
Sessionを変更せず閲覧対象を変える操作で、 既にactiveなSessionを表示すれば送信可能になり得る。

| --------------------- | -------------------------------------------------------------------------------------------- |

| `cancelled`           | 直近の実行がキャンセルされた                                                                 |
| `failed`              | 直近の実行が失敗した                                                                         |
| `interrupted`         | 直近の実行が中断された                                                                       |

| `settlement running`  | Worker・子プロセスの終了処理まで含めた実行が継続中                                           |
| `settlement settling` | Coreの状態が終了処理中で、終了処理の完了はまだ確認されていない                               |

| `settlement unknown`  | 終了処理の完了を確認できない。保存履歴からの閲覧などで表示される                             |

| ----------------------- | -------------------------------------------------------------------------------------- |

### 操作通知・エラー

通知は操作結果や問題の理由に応じて変わるため、表示文言を種類ごとにまとめる。

| 種類・表示例                                                                       | 説明                                                                         |
| ---------------------------------------------------------------------------------- | ---------------------------------------------------------------------------- |
| 受付拒否：`submission rejected: …`                                                 | 入力がCoreに受け付けられなかった理由                                         |
| 受付結果不明：`submission unconfirmed …`                                           | 受付を確認できない。draftの保持や、再送前のCore確認を案内する                |
| 応答確認中：`submit response unknown · checking command`                           | 送信応答が不明なため、Coreにcommandの結果を問い合わせている                  |
| 操作待ち：`Session operation still pending`など                                    | 先行するSession操作や入力の受付確認が終わっていない                          |
| 操作不可：`task.submit unavailable for this Session`など                           | 現在のSessionでは指定した操作を利用できない                                  |
| キャンセル結果：`cancel requested`、`cancel unconfirmed`、`cancel rejected: …`など | キャンセル要求の受付結果。実行の終了とは別の通知                             |
| Session一覧・閲覧・切替の進捗とエラー                                              | 一覧取得、別Sessionの閲覧、新規作成や再開の途中経過、失敗理由                |
| 改名：`Session renamed`／`Session title unchanged`                                 | Session名を変更した／既存の名前と同じだった                                  |
| recallの進捗・結果・エラー                                                         | 過去の実行内容の参照準備や、その解除の状況                                   |
| context取得の進捗・エラー                                                          | checkpoint・recall・直近requestの短い情報・active configを読む画面の取得状況 |
| provider・model・effortの取得や変更の通知                                          | カタログ取得、選択変更、保存失敗などの案内                                   |
| 認証登録の結果：`credential saved: …`など                                          | 認証情報の保存や、その有無の再確認の結果                                     |
| パス補完の通知                                                                     | Coreのworkspaceパス取得、候補数、補完失敗などの案内                          |
| 入力履歴：`history empty`／`history boundary`                                      | 入力履歴が空／これ以上前後へ移動できない                                     |
| 入力のエラー：`paste exceeds 64 KiB`／`input too long`                             | 貼り付けや入力が現行の入力上限を超えた                                       |
| コマンドのエラー：`unknown command …`／`usage: …`                                  | 不明なコマンド、または引数の使い方の案内                                     |
| 改行操作の案内                                                                     | 端末から届くキー形式に応じた改行操作の説明                                   |
| Core終了の拒否・エラー                                                             | Coreの終了要求が受け付けられなかった、または結果を確認できない               |

## 2行目 — 実行状態・workspace・Session

| 要素・表示例                         | 説明                                                                                                           |
| ------------------------------------ | -------------------------------------------------------------------------------------------------------------- |
| `⠋`などのspinner                     | 実行・キャンセル処理中であることを示すアニメーション                                                           |
| `working`                            | 現在の実行が進行中                                                                                             |
| `cancelling`                         | 取消要求を送って停止を待つ表示。API応答前のTUI側待ちも含み、Coreが受付済みとは限らない                         |
| `00:12`／`1:02:03`                   | execution作成時刻（createdAt）からの経過時間。取消要求からの時間ではなく、同じ実行への再接続でも起点を引き継ぐ |

実行中の状態表示はこれらより優先する。

## 現行スラッシュコマンドとショートカットの対比

端末から同じ制御文字が届くCtrl-I（Tab）、Ctrl-J／Ctrl-M（Enter）、Ctrl-[（Esc）も、
同じ入力として処理される。独立した操作の割当ではない。
Ctrl-L・Ctrl-N・Ctrl-P・Ctrl-R等は現行decoderで未割当のため、有効なショートカットの表には含めない。

### S27と合わせて整理する論点

ショートカット整理のS27は、[Increment 159](../increments/increment-159.md)へ計画化した。
利用者が挙げたS23はResponsesの表示順・履歴本文欠落の修正で、
[Increment 137](../increments/increment-137.md)として完了済みの別件だった。

フッター整理とS27を合わせる検討では、次を一つの操作案内として揃える。

- 改行・送信・steering・follow-up・キャンセルの意味とキー割当。
- 同じ操作に対応するスラッシュコマンドとキーの説明。
- 1行目に残す現在操作と、helpへ移す固定操作。最新案ではhelpは`/help`、F1はSession一覧。
- 履歴閲覧・overlay表示中のEnter／Esc／Ctrl-Cの優先順。

Alt-Enterの現行差は、legacyのESC＋Returnとxterm形式が`alt_enter`へdecodeされ、
入力待ちは改行・実行中はfollow-upになる一方、CSI-uのAlt-Return（`CSI 13;3u`）は
`newline`へdecodeされ、実行中でも改行になること。
「Alt-Enterを常に改行へ統一し、予約を別キーにする」は候補であり、割当は未決。

この追記は比較・整理案の文書化であり、キー割当・フッター・helpの実装変更は行っていない。

| 改行                     | 本来はShift-Enterが希望。ただしGhostty＋tmuxでは機能せず、Alt-Enterのみ動く | 第一希望のShift-Enterと現環境で動くAlt-Enterを区別して記録。最終割当と予約キーは未決                                                  |

| 次タスク予約・追加指示   | 最新提案はF2＝予約、F3＝追加指示。明示的に「送り込む」操作                  | rootも推奨。実行中のEnterで追加指示を送る割当を外す案。実装採用は未決                                                                 |

| `/edit`                  | エディタ起動をいつか実装したい                                              | 通常利用メモS29に将来候補として記録。通常入力の削除キーを省く方向に関連するが、今回の実装対象に含めない                               |

Ctrl-Hは現行decoderで`0x08`としてBackspaceと同じ`backspace`eventになる。
Backspaceから`0x08`が届く場合、受信側ではCtrl-Hとの区別ができない。
したがって「Ctrl-Hを独立した案内・割当として省く」ことと、Backspaceの受信を削ることを分ける。
案内からCtrl-Hを省いても、Backspaceの正常な入力経路は維持する案とする。

Alt-Enterを改行に統一する場合、現在の実行中follow-up予約との二重用途を解消する必要がある。
最新の利用者提案はF2を予約、F3を追加指示に割り当てる。元のastra画面例の`Alt-Enter queue`は更新前の割当を前提とした例である。
本格コマンドピッカーは未採用・未実装。現行の候補表示・Tab補完と区別し、rootは今回一緒に作る案を推奨した。

### workspaceパス補完の現行起動条件

利用者は起動条件の説明後、この機能の廃止を選んだ。以下は廃止前のcurrent sourceの調査記録。

1. picker・help等を開いていない通常入力画面でTabを押す。実行中でもこの入力経路はある。
2. 入力全体が`/`で始まる場合はslashコマンド補完へ進み、パス補完は起動しない。
3. それ以外では、カーソル位置から空白・Tab・改行まで遡った文字列をパスの先頭部分として探す。
   `@`等の起動記号や、自動表示はない。
4. Coreのworkspace内の相対ファイルパスが対象。`v0/tui/remote_sess`や
   `./v0/tui/remote_sess`のような接頭辞を使う。絶対パス、空の接頭辞、`./`だけでは補完しない。
5. 一致が一件なら、たとえば`"./v0/tui/remote_session.ts"`という引用符付き相対パスへ置換する。
   複数一致は`path match ambiguous (N)`、一致なしは`no path match`をフッターへ通知する。
   候補一覧を開いたり、共通部分まで伸ばしたりはしない。
6. Coreのパス一覧を取得できない・一覧が不完全な場合は`path index unavailable`。
   最初の取得結果をCore側・TUI側で保持するため、追加ファイルの自動再取得も現行にはない。

source確認に加え、2026-09-29に本workspaceを同じindex生成・補完関数でread-only確認した。
一覧はcomplete、候補1014件で、`v0/tui/remote_sess`から
`"./v0/tui/remote_session.ts"`への補完が成立した。
通常TUIのTab操作や利用者の稼働Coreの一覧を確認した結果ではない。
広い接頭辞で複数候補になると一覧が出ないため、機能を見かけにくい経路はcurrent sourceから確認できる。
