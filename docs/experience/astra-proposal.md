### ターン中の本文へ表示するメッセージ

通常の入力、追加指示、thinking、tool、assistant本文は既存の会話表示を使う。
以下の運用通知の表示内容と保持範囲は、2026-09-29に利用者が「いまの案で良い」と了承した。
運用通知は`system>`へ揃える。

| 表示するもの                            | 内容・扱い                                                                                          |
| --------------------------------------- | --------------------------------------------------------------------------------------------------- |
| 実行の失敗・取消・中断・結果不明        | 結果と得られる短い理由。受付の結果とは分け、次のsnapshotやtypingで消さず見返せるようにする          |
| 入力の受付拒否・受付確認不能            | 対象入力と理由、保持された入力、次に確認すべきこと。確認不能を拒否確定と扱わない                    |
| キャンセル要求の拒否・確認不能          | 停止できたか確認できないかを説明。実行結果のcancelledと区別                                         |
| 次タスクの予約・開始・未開始            | 予約内容と状況。現在タスクの成功後に開始し、失敗・取消等では開始せず内容と理由を残す                |
| 追加指示の受付                          | 対象入力が反映されたことを本文で確認。入力の表示と重複する汎用accepted通知は重ねない                |
| Session・設定・認証・recall等の操作失敗 | 対象操作、結果、短い理由                                                                            |
| credential保存・recall準備／解除の結果  | 通常画面だけでは分かりにくい結果を短く表示。credentialの値は含めず、保存成功をAPI認証成功と呼ばない |
| 接続断                                  | 一度の出来事として通知。現在の接続状態は2行目にも表示                                               |

通常のタスク受付成功、正常終了のcompleted、画面の更新で分かる改名・model変更成功は独立通知を省く案。
pickerのloading/savingはpicker内、引数usageや入力履歴の端などはその場の入力補助として扱う。
すべてのnotice文字列を本文へ蓄積する案にはしない。

色の案は、通常通知を通常文字色、失敗だけ`system>`ラベル・短い失敗語を赤。
HTTP経路での停止理由取得とsnapshot更新後の通知保持は、実装時に成立させる必要がある。

#### 本文で見返せることとSession履歴への保存

利用者の「ターン中メッセージは履歴に残るんだっけ？」に対する確認。
この案の「本文に残す」は、TUI内でsnapshot更新・typingの後も見返せる表示を意味し、
全通知のSession履歴への永続保存を含まない。`system>`は表示ラベルで、保存の指定ではない。

| 対象                                                       | 現行の保持・保存と、この案の範囲                                                                                                                                                  |
| ---------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 通常の入力・追加指示・assistant・tool等                    | 既存のCore履歴に保存する経路がある。追加指示はsemantic eventとして反映された内容と、受付待ちの通知を区別する                                                                      |
| 実行の終了結果                                             | 既存のexecution／semantic記録に保存される。本文のsystem>へ再表示する処理は今後の実装。短い停止理由の具体的な取得経路は未確認                                                      |
| 次タスクの予約・未開始等                                   | 現行はCoreのメモリ内に記録し、同じ稼働CoreへTUIが再接続すればsnapshotから再表示する。Core再起動後に予約記録を復元する保存経路はない。予約が実際に開始された後の入力・実行記録は別 |
| 受付確認不能・取得／保存失敗・接続断などのローカル操作通知 | この案はTUI内で保持する範囲。TUIを終了して再起動した後の同じ通知文の復元は含めていない                                                                                            |
| pickerのloading・補完・usage等                             | 操作中の一時表示。Session履歴への保存対象としていない                                                                                                                             |

今回の了承はこの表の保持範囲であり、全通知の永続保存は追加しない。将来その範囲を変える場合は別に検討する。
既存記録から表示を復元することと、通知文そのものを保存することも分けて決める。 参照:
`remote_session.ts`のrenderSnapshot、`state.ts`のnotice表示とconversation_projection、
`task_service.ts`のfollow-up records、production history storeのexecution_settled保存。

#### コマンドピッカーの採用状況と推奨

本格的なコマンドピッカーは未採用・未実装。現行はslash候補の表示とTab補完である。
rootは今回の整理と同時に、入力先頭の`/`で開くピッカーを作る案を推奨する。
コマンド名を入力して候補を絞り、↑／↓で選び、Enterで入力欄へ補完し、Escで閉じる。
補完後は必要な引数を入力し、Enterで実行する。ヘルプも`/help`候補から選べる。
これは今回提示する実装候補であり、利用者が既に採用した機能とは扱わない。

#### 短い待機区間を個別の状態名にしない推奨

利用者はsubmitting、preparing、shutting downが短く、読めないのではないかと指摘した。
実処理時間は測定していない。rootの最新推奨はsubmitting・preparingをworkingへまとめ、 shutting
downのフッター表示を省くこと。採用はまだ確定していない。

この案のworkingは新規タスク送信から終了までの処理中を表し、provider実行開始の確認を意味しない。
実行情報が届くまでは経過時間を出さず、取得後は既存のexecution.createdAtを起点に表示する。
送信の拒否・確認不能や終了の失敗は、了承済みの本文メッセージで説明する。
既に実行中のタスクへの追加指示・予約の送信ではworkingを維持し、受付の反映・結果は本文で確認する。
状態名を読ませるための人工的な待ち時間は設けない。

```text
[ready │ …/henji-harness │ session:4de84efc │ <タイトル>]
[⠋ working 00:12 │ …/henji-harness │ session:4de84efc │ <タイトル>]
```

readyは新規タスクを開始できる状態を意味する。working中も入力編集と追加指示はできる。
accepted、completed、canonical、settlementはフッターから削除し、どのタイミングにも表示しない。
内部記録・APIにある意味は保持する。取消・失敗等の実行結果は、了承済みの本文メッセージで表示する。

### 実行中の追加指示と予約の違い

| 操作                            | 入力の用途                    | 反映される先                               | キー案           |
| ------------------------------- | ----------------------------- | ------------------------------------------ | ---------------- |
| 追加指示（steering）            | 「この変更ではAも考慮して」   | 現在のタスクの続きに反映                   | F3（利用者提案） |

同じ入力欄を使うが別操作。予約は失敗・取消等の場合には開始せず、内容と理由を残す。

実行中の通常入力はEnterで送らず、F2／F3で送り先を明示的に選ぶ案。
slashコマンドの実行とpicker内の選択には、実行中もEnterを使う。
F3は現在タスクの続きへの追加指示であり、providerの応答やtoolをその場で中断する操作ではない。

## 元のastra提案・検討記録

## 推奨

1行目を「いま使う操作」、2行目を「現在状態とSession」、3行目を「provider・model・effort」へ揃える。
操作結果や失敗は本文の`system>`へ移す。

1行目をslash専用にするより、通常は`Enter submit`、実行中は`Enter steer`・`Alt-Enter queue`・
`Esc cancel`を残す方が使いやすい。同じ入力欄でも実行状態によってEnterの意味が変わり、
履歴閲覧ではEscの意味も変わるため、F1だけへ移すと現在の操作が画面から分からなくなる。

`Ctrl-C clear`・`Ctrl-D detach`・`Ctrl-Q shutdown`などの固定操作はF1へ集約できる。
`/detach`・`/shutdown`はslash候補でも発見できるようにする。
元のastra提案はキー割当を維持する前提。後述のS27との統合検討では、割当も合わせて決める。

この案は構想の「人間は外部文書やhelpを先に読まなくても、依頼を入力し、処理中か入力待ちかを知る」
という要件にも沿う。

| pickerのロード中・保存中                           | そのpicker内                                                                   |
| パス補完候補・入力履歴の端・引数usage              | 操作中の入力補助。1行目または候補表示で短く案内                                |
| workspace・Session ID・タイトル                    | 2行目を維持                                                                    |
| provider・model・effort                            | 3行目を維持                                                                    |

すべての`notice`文字列を本文に流すことは推奨しない。
入力履歴の端に来るたびに`system> history boundary`が積み上がったり、pickerを開くたびに
`loading model catalog`が残ったりすると、本文が読みにくくなる。
後から意味を持つ結果通知と、その場だけの操作補助を分ける。

## 状態と実行結果の分離

通常の流れは「ready → 送信中 → 実行準備 → working → ready」。
途中で受付済みだがsnapshot未反映なら、「受付済み・状態更新待ち」と表示する。
実行中のsteering送信によって、主状態を`working`から単なる`steering`へ置き換える必要はない。

キャンセル要求の受付と実行終了も分ける。
要求を送った段階では`cancelling`、実際に終了した段階で本文にキャンセル結果を出す。
拒否や確認不能なら、その理由を本文へ残す。

`ready`は「直近の実行が成功した」ではなく「いま次のタスク入力を受け付けられる」。
失敗後でも入力可能なら`ready`となる。実行結果がcompletedでも、受付や終了処理のため次入力を
受け付けられないなら、まだ`ready`にはしない。
`settlement`という内部項目を常設せず、実際に次入力をまだ送れない状態を短く示す。

判定は既存のpending状態、接続状態、表示対象Session、`runtime.operations`を使う。
新しい拒否条件を追加する提案ではない。

## 軽いslash案内とコマンドpicker

| 方式             | 利点                                                                               | 残る課題                                                               |
| ---------------- | ---------------------------------------------------------------------------------- | ---------------------------------------------------------------------- |
| 軽い候補案内     | 現在の入力・Tab補完を活かせる。フッター整理の変更量が小さい                        | `/`だけで全候補を1行に並べると読みにくい。説明と引数案内が不足しやすい |
| 選択できるpicker | 14個の既存コマンドを一覧で見つけられる。説明、引数、detach／shutdownの違いを示せる | 候補選択、editor、Esc、既存picker間の操作を設計する必要がある          |

最小incrementでは軽い候補案内を採用し、その後にpickerを別incrementで追加することを推奨する。
今回の混在はpickerなしでも解消でき、pickerを先に作っても状態・結果・受付通知の混在は別途直す必要がある。

将来のpickerはフッター1行を一覧そのものにせず、入力欄に隣接した候補表示にする。

- 入力欄先頭の`/`で候補を開き、続けて入力するとコマンド名を絞る。
- 上下で候補を選び、EnterまたはTabで入力欄へ補完する。選択ではコマンドを実行せずpickerを閉じる。
- 完全なコマンドを直接入力した場合は従来どおりEnterで実行する。
- `/rename`・`/view`など引数が必要なものは、補完後に空白を付け、入力欄近くにusageを示す。
- `/resume`・`/recall`の省略時動作は既存仕様を保ち、候補説明で示す。
- `/provider`・`/model`・`/effort`・`/sessions`は既存pickerを開く。各機能をコマンドpickerへ重複実装しない。
- Escは候補を閉じてdraftを残す。そのEscを同時に実行キャンセルへ渡さない。既存overlayの操作順序と揃える。
- `/login`は既存のmasked入力へ進め、コマンド欄へcredentialを入力させない。

「候補選択は補完、完成したコマンドのEnterは実行」という操作区別は、採用前に利用者へ提示する選択事項。

## F1ヘルプ

完全な操作一覧として、送信・steering・follow-up、改行、入力編集、履歴閲覧、Session操作、
detach、shutdownを目的ごとにまとめる。特に次の違いを明記する。

- steeringは現在の実行への追加指示。
- follow-upは現在の実行の成功後に行う予約。失敗・キャンセル時は保持された内容と理由を確認する。
- detachはTUIを離れる操作で、Coreと受付済み作業は継続する。
- shutdownはCoreを終了し、他の接続UIにも影響する。
- Ctrl-Cはdraft clearであり、実行キャンセルではない。

元のastra提案ではキー割当の問題を未採用のS27に残す方針だった。
利用者の追加発言を受け、後述の統合検討ではフッター・F1とキー割当を一緒に整理する案へ広げる。

## system>の色と通知の生存期間

本文通知のラベルは`system>`へ統一してよい。色と寿命はラベルと別に決める。

通常通知は端末の通常文字色を基本にし、ラベルだけを控えめな色にする。
現行の紫が利用者の端末で強く見えるなら、通常文字色へ寄せることを推奨する。
失敗だけは`system>`のラベルや短い失敗語を赤にし、本文全体を赤くしない方が理由を読みやすい。
受付結果不明は「未確認」という文言を残し、色だけで意味を伝えない。

| 種類                                                                 | 本文での扱い・生存期間                                        |
| -------------------------------------------------------------------- | ------------------------------------------------------------- |
| 普通のタスク受付成功                                                 | 省略。反映された入力と現在状態で確認                          |
| steering受付・follow-up予約                                          | Core snapshotの対象入力／予約を表示。対象の変化に合わせて更新 |
| 正常終了                                                             | 独立したcompleted通知は通常省略                               |
| 失敗・中断・キャンセル・結果不明                                     | 実行結果として残す。typingや次snapshotで消さない              |
| 受付拒否・受付確認不能                                               | 理由、draftの扱い、次に確認すべきことを残す                   |
| 改名・model選択成功                                                  | 更新後の2／3行目やpickerで確認できる場合は重複成功通知を省略  |
| credential保存・recall準備など通常画面だけでは結果が分かりにくい操作 | 短い結果通知を残す。credentialの値は含めない                  |
| 保存・取得・操作の失敗                                               | 理由を残す。対象picker内で解決できるものはpickerにも表示      |
| loading・polling・snapshot待ち                                       | 一時表示。終われば結果または現在状態へ置き換える              |
| 入力履歴の端、補完候補、usage                                        | 操作中だけの補助。本文へ積み上げない                          |
| 接続喪失                                                             | 本文に一度記録し、2行目にも現在の接続状態を表示               |

一時表示は「数秒で消す」より、「その操作が終わるまで」「入力補助の対象が変わるまで」を寿命にする。
失敗理由は数秒で消さず、見返せる方が有用。

## 本文移動の具体的な注意

### snapshot更新で通知が消える

現在のHTTP接続TUIではsnapshot更新時に本文entriesを置き換える。
`remote_session.ts`の`renderSnapshot`が`setConversationEntries`を呼び、
`state.ts`の`applyConversationProjection`が一覧を再構成する。
既存noticeを単に`eventSink`へ変更するだけでは、次snapshotで通知が消える。

最小限必要なのは、既存の本文表示へ次を合成すること。

- Coreにある実行結果・steering・follow-upは、Core snapshotや既存読出し結果から投影する。
- そのTUIで行った改名、補完、受付確認等の操作通知は、TUI内の表示状態として保持し、
  同じSessionのsnapshot更新でも消さない。

後者を新たなSession履歴authorityへ保存する必要はない。 別TUIへローカル操作通知を共有する必要もない。
同じTUIの通信再接続では保持し、別Sessionに無関係な通知を混ぜない。

Core事実の通知は、同じ実行・予約をsnapshot更新ごとに追加せず、同じ対象の表示として扱う。
現在follow-up／steeringをsnapshotから再表示する経路も合わせて扱う。
履歴閲覧中に通知が増えても最新位置へ強制移動せず、既存の新着案内を使う。

### HTTP経路で失敗理由の本文投影が不足している

`snapshot_presentation.ts`はmessages・tools・thinkingを投影しているが、実行終了のoutcomeや
失敗理由を一般的な本文通知として投影していない。
`state.ts`のlegacyな`failure_diagnostic`表示が存在することは、通常HTTP経路で失敗理由が見える証拠ではない。

現行`ExecutionView`にはoutcomeと`diagnosticId`はあるが、失敗理由の本文はない。
確認したsourceで保証できる最小表示は、たとえば次の形である。

```text
system> 実行に失敗しました。execution 1234abcd
```

これを「理由も移せた」と扱わない。
採用後は、既存semantic記録から停止理由を取得する読出し経路を限定して確認し、
短い理由を本文へ投影できる範囲を確定する必要がある。
新しい通知保存基盤や履歴authorityを作る提案ではない。
既存APIで理由を渡せない場合は、必要な短い理由をどう渡すかを追加判断へ戻す。

確認が済むまではfailed等をフッターから削除しただけで通知移動を完了扱いにしない。
直近実行の結果表示と、過去の全実行結果を遡って復元する機能は別範囲。
後者まで今回追加する提案ではない。

## 最小incrementと未決事項

推奨する最小incrementは、状態と操作案内の分離、結果・操作通知の表示先整理、F1の整理、
軽いslash候補案内まで。

layoutがstatus文字列を分解して役割を推測する方式も、変更範囲では状態・操作・通知を
別の表示入力として渡す方が、accepted残留のような混在を解消しやすい。

完了確認は隔離XDGのproduction TUIをtmuxで使い、通常入力、実行中入力、キャンセル、
本文通知とsnapshot更新、履歴復帰、Session閲覧、既存picker、接続状態の表示を実際に確認する。
実provider callが必要な確認は、対象・回数・保存先を示して別途承認を得る。
本相談ではコード変更・実行・provider requestを行っていない。

利用者へ戻す主な選択:

1. 1行目に文脈依存のEnter／Esc案内を残すか。推奨は残し、固定shortcutをF1へ移す。
2. pickerを今回同時に作るか。推奨はフッター整理を先に完了し、pickerを別incrementにする。
3. system>の色。推奨は通常通知を通常文字色、失敗だけラベル・短い失敗語を赤にする。

送信準備／受付待ち等の一時状態を2行目にどこまで表示するかも、利用者が支持した基本遷移
`ready → working → ready`と区別して採用判断する。上記の細かな一時表示はastraの提案であり、
合意済み仕様として扱わない。

| picker・補助画面を閉じる | 対応なし           | Esc / Ctrl-C                                                | 実行をキャンセルせず閉じる。F1ヘルプはF1でも閉じる。保存処理中等はpicker側の受付状態に従う            |

Ctrl-DとCtrl-Qはoverlay表示中にも処理される。通常のEnter／Escはoverlay内の選択・閉じる操作が優先される。
コマンドpickerの追加や、送信・キャンセル等への新しいスラッシュコマンド追加はまだ決まっていない。

端末から同じ制御文字が届くCtrl-I（Tab）、Ctrl-J／Ctrl-M（Enter）、Ctrl-[（Esc）も、
同じ入力として処理される。独立した操作の割当ではない。
Ctrl-L・Ctrl-N・Ctrl-P・Ctrl-R等は現行decoderで未割当のため、有効なショートカットの表には含めない。

Ctrl-Hは現行decoderで`0x08`としてBackspaceと同じ`backspace`eventになる。
Backspaceから`0x08`が届く場合、受信側ではCtrl-Hとの区別ができない。
したがって「Ctrl-Hを独立した案内・割当として省く」ことと、Backspaceの受信を削ることを分ける。
案内からCtrl-Hを省いても、Backspaceの正常な入力経路は維持する案とする。

Alt-Enterを改行に統一する場合、現在の実行中follow-up予約との二重用途を解消する必要がある。
新しい予約キーはまだ選んでいない。元のastra画面例の`Alt-Enter queue`も、更新前の割当を前提とした例である。

### workspaceパス補完の現行起動条件

利用者は起動条件の説明後、この機能の廃止を選んだ。以下は廃止前のcurrent sourceの調査記録。

1. picker・help等を開いていない通常入力画面でTabを押す。実行中でもこの入力経路はある。
2. 入力全体が`/`で始まる場合はslashコマンド補完へ進み、パス補完は起動しない。
3. それ以外では、カーソル位置から空白・Tab・改行まで遡った文字列をパスの先頭部分として探す。
   `@`等の起動記号や、自動表示はない。
4. Coreのworkspace内の相対ファイルパスが対象。`v0/tui/remote_sess`や
   `./v0/tui/remote_sess`のような接頭辞を使う。絶対パス、空の接頭辞、`./`だけでは補完しない。
5. 一致が一件なら、たとえば`"./v0/tui/remote_session.ts"`という引用符付き相対パスへ置換する。
   複数一致は`path match ambiguous (N)`、一致なしは`no path match`をフッターへ通知する。
   候補一覧を開いたり、共通部分まで伸ばしたりはしない。
6. Coreのパス一覧を取得できない・一覧が不完全な場合は`path index unavailable`。
   最初の取得結果をCore側・TUI側で保持するため、追加ファイルの自動再取得も現行にはない。

source確認に加え、2026-09-29に本workspaceを同じindex生成・補完関数でread-only確認した。
一覧はcomplete、候補1014件で、`v0/tui/remote_sess`から
`"./v0/tui/remote_session.ts"`への補完が成立した。
通常TUIのTab操作や利用者の稼働Coreの一覧を確認した結果ではない。
広い接頭辞で複数候補になると一覧が出ないため、機能を見かけにくい経路はcurrent sourceから確認できる。

## 現行要素そのものの整理案（root追記、2026-09-29）

利用者の「現行要素自体も整理できそう」という発言を受けた追加案。
現行一覧の項目をそのまま別の場所へ配るだけでなく、同義の表記、重複する成功通知、
操作ごとの冗長な案内を減らす。以下は既に支持された方向を含むrootの整理案であり、
表全体が採用済みという意味ではない。

| 現行要素                                                                                  | 整理後の扱い                                                                             | 残す意味                                                                     |
| ----------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------- |
| `ready`／`idle`                                                                           | `ready`へ統一                                                                            | 新規タスクを開始できるか                                                     |
| 通常タスクの`accepted`、正常終了の`completed`                                             | 独立した成功通知を省く                                                                   | 入力の反映、`working`、次入力可能時の`ready`で確認                           |
| `submitting`、`awaiting receipt`、`processing`、`accepted … syncing snapshot`等の複合表示 | 操作ごとの冗長な組合せをまとめ、その時点で待っているものを一つ示す案。詳細と表示先は未決 | 受付を確認できたか・何を待っているか。受付確認不能や拒否は別の結果として残す |
| `canonical`／`non-canonical`、`settlement …`                                              | 通常画面の独立要素を省く                                                                 | 内部記録・APIでの確認能力                                                    |
| `cancelled`／`failed`／`interrupted`／結果不明                                            | 本文の`system>`で理由を含む結果通知へまとめる                                            | 結果の違いと、人間が次の判断に使う理由                                       |
| 改名成功、タイトル変更なし、provider／model／effort変更成功                               | 更新後のタイトル・選択値が見えるときは成功通知を省く                                     | 操作後の実際の値。変更失敗は理由を通知する                                   |
| pickerのloading／saving、操作ごとの取得中通知                                             | 対象picker内の一時表示へまとめる                                                         | その操作がまだ終わっていないこと                                             |
| 受付拒否、確認不能、取得失敗、保存失敗等                                                  | `system>`の「対象＋結果＋理由」を共通の書き方にする                                      | 理由と受付の確かさ。確認不能を失敗確定へ置き換えない                         |
| `history start`、`history record N of M`、`history`、`new below N`                        | 履歴位置と新着件数を一つの案内にまとめる。例えば`history N/M │ new K`                    | どこを見ているか・下に更新があるか。`Esc latest`もその場の操作として残す     |
| `credential present`の常設案内                                                            | 認証設定画面の情報へ集約                                                                 | 認証情報の有無。未設定で操作に影響する場合は案内する                         |
| 入力履歴の端、引数usage、補完候補                                                         | 入力補助として短く表示し、対象操作の終了で置き換える                                     | 現在の入力操作への手掛かり。本文へ繰り返し蓄積しない                         |
| キーの別名、同じ操作の二重割当、改行方法専用キー                                          | 利用者の追加判断に沿って割当・案内を減らす                                               | Backspace、改行、クリア等の実際に使う操作                                    |

正常時の常設情報は、現在状態、現在成立する操作、workspace／Session、provider／model／effortに絞る案。
READ-ONLYやDISCONNECTEDは新規タスク送信可否・接続の意味が異なるので、現在状態の必要な補足として扱う。
失敗後も次入力を送れるなら`ready`へ戻り、失敗理由は本文に残る。
失敗理由のHTTP本文投影やsnapshot更新時の通知保持は、前述の実経路確認を必要とする。

スラッシュコマンドは、まず目的別にhelpへまとめる。

- Session操作: `/new`、`/sessions`、`/view`、`/resume`、`/rename`。
- 実行設定: `/provider`、`/model`、`/effort`、`/login`。
- context確認・参照準備: `/context`、`/recall`。
- help・接続・終了: `/help`、`/detach`、変更方針の`/quit`。

この分類だけでコマンド数の削減を決めない。`/view`と`/resume`、`/context`と`/recall`には
現在異なる操作結果がある。統合するなら、その操作をどこから行えるようにするかを先に決める。
コマンドと同じ目的のキーは、`/sessions`とF2候補のように、名前で発見する入口と素早く操作する入口として扱える。

`@`と`/edit`は将来メモのまま。今回の要素整理へ実装を加える案にはしていない。

## 現行要素の意味整理（gpt-6-astra追加相談、2026-09-29）

利用者の追加依頼により、gpt-6-astraへ現行要素の意味をsourceに照らして整理させた。
全表示種類、14コマンド、キー操作を対応させた結果は
[現行要素の意味整理](astra-element-meanings.md)にまとめた。 表示・割当の実装は変更していない。

混在の中心は、次の四つの問いだった。

| 問い                          | 答える要素                               |
| ----------------------------- | ---------------------------------------- |
| このSessionでいま何ができるか | ready、操作案内、READ-ONLY               |
| いま何が動いているか          | working、cancelling、経過時間            |
| 先ほどの操作がCoreへ届いたか  | accepted、受付確認中、受付拒否・確認不能 |
| その実行がどう終わったか      | completed、cancelled、failed等と理由     |

同じ意味にまとめる前に残すべき違い:

- readyは新規タスクを開始できる状態。working中も編集・追加指示はできる。
- cancellingは現行ではTUIの取消要求待ちも含む。requestedは受付結果、cancelledは実行結果。
- viewは閲覧対象を変える。resumeはCoreの作業対象も変える。active
  Sessionをviewすれば送信可能になり得る。
- contextは直近requestの短い情報も含む読取。recallは過去executionの参照を次タスクへ準備する変更。
- steeringは現在のexecutionへ、follow-upは正常終了後の別タスクへ送る。予約の受付はworkingだけでは確認できない。
- provider変更はmodel・effortも変更する。model変更はeffortも変更する。三項目の連動を説明する必要がある。
- 本文の履歴位置、入力履歴、表示更新の新着件数は、それぞれ対象と件数の単位が異なる。
- detachとquitは、TUIだけを離れるかCoreも終了するかが異なる。

以上に基づいて現行一覧のready、cancelling、経過時間、context、選択設定の説明を補正した。
元の配置案・root案に対する詳しい補正と未決事項も追加相談文書を参照する。
